# Phase 7CM — Index / Source Selection Runtime Workflow

## Purpose

7CM starts remediation of `DASHBOARD_RUNTIME_INTERACTION_NOT_WIRED`, the hard blocker found during attempted 7CZ final certification. The blocker existed because the dashboard generated by `scripts/run_analysis.py` exposed visible workflow controls that were preview-only or inert and did not submit to governed Phase 7 runtime/backend workflow handling.

The 7CM scope is intentionally narrowed to `index.html` source intake and source selection handoff only. It adds an active governed source-selection action path while preserving the Phase 7 safety boundary. The dashboard can render controls, payload metadata, and client-side bridge calls, but the governed action contract and request handling live outside `html_dashboard.py`. Screens 1–6 and cross-screen integration remain pending for 7CN–7CT.

## Active Interaction Architecture

The active interaction path has three parts. First, `src/reporting/html_dashboard.py` renders the index source-selection controls with screen, action, workflow, target, governance, execution, idempotency, source metadata, and safety metadata. Second, `src/learning/dashboard_runtime_interaction.py` defines and validates the common governed dashboard action payload plus source lookup/validation helpers. Third, `scripts/dashboard_workflow_service.py` provides local JSON endpoints that validate source requests and queue audit-safe records:

- `/phase7/dashboard/actions` accepts final governed source-selection handoff requests.
- `/phase7/dashboard/existing-runs` performs service-side DB lookup for persisted run choices when the DB is configured.
- `/phase7/dashboard/object-storage/validate` validates Object Storage metadata through the governed service path.

The browser bridge posts requests to a configurable governed workflow API only when an operator clicks a 7CM governed control. The local/demo default is `http://127.0.0.1:8765/phase7/dashboard/actions`, but the dashboard first honors `window.PHASE7_DASHBOARD_ACTION_ENDPOINT` and derives the sibling Existing Run and Object Storage validation endpoints from that configured base. Deployments may also set `window.PHASE7_DASHBOARD_EXISTING_RUN_LOOKUP_ENDPOINT` and `window.PHASE7_DASHBOARD_OBJECT_STORAGE_VALIDATE_ENDPOINT` explicitly. If the service is unavailable, the UI reports failure. It does not silently pretend success.

The active operational controls are rendered above legacy preview panels on `index.html`. Older 7BQ/7BR/7BS/7BT preview-only panels are marked as historical read-only context for prior subphase boundaries and are not the current workflow.

## Safe Local / Demo Model

The local service queues governed request records under an environment-configurable directory, `AWR_PHASE7_DASHBOARD_ACTION_QUEUE`, or an operating-system temp directory by default. This gives local/demo dashboard actions a real request, validation, response, and audit representation without requiring production DB writes.

For local demos, `scripts/run_analysis.py` checks whether the local service is listening on the configured local endpoint and starts `scripts/dashboard_workflow_service.py` when needed. This startup path is only for the local development/demo endpoint. If `PHASE7_DASHBOARD_ACTION_ENDPOINT` points to a non-local governed workflow API, the generator does not start a localhost service.

OCI deployment remains a backend/API concern: the browser should call an OCI-hosted governed workflow API, not Object Storage or the database directly. Object Storage validation uses backend service identity and configuration, the browser never receives OCI credentials, and backend validation/staging owns durable source handling.

The local queue is not diagnostic truth and is not parser output. It is a governed source-selection request intake record that can later be routed through the existing Phase 7 repositories and controllers.

## Supported Source Inputs And UX

7CM supports these source modes at the request-contract level: `local_staged`, `local_file`, `existing_run`, and `object_storage`. Local folder and file controls use OS file/folder pickers for local development or upload-style staging. Object Storage metadata is first-class because it is the OCI-ready durable source path. The browser never calls Object Storage directly and never receives credentials.

For local files and local folder candidates, the verified parser path is `.out` text AWR reports. `scripts/run_analysis.py` uses `src.loader.awr_loader.load_awr_sources`, which discovers only `*.out`, and current parser/loader tests do not prove `.txt`, `.html`, or `.awr` equivalence. Therefore 7CM accepts `.out` only. HTML AWR input is planned for a future parser/source adapter, including HTML table/section extraction and source normalization into the deterministic parser pipeline. No HTML parser support is implemented in 7CM.

The visible index workflow keeps OS picker selection separate from governed submit. The Local folder control is labeled "Choose Folder"; the documentation notes that the browser-native dialog may use "Upload" wording, but that this is only local file/folder selection for the governed request. After selection the UI says that files are available for governed validation and nothing has been submitted yet. The governed request/audit record is created only when the operator clicks the source-specific submit control, such as "Submit Local Folder Source Handoff" or "Submit Object Storage Source Handoff."

Existing run selection is not a blind text box. The operator clicks "Load Existing Runs," the service queries local/dev DB persistence or the configured governed persistence API, and the UI shows selectable run choices. Object Storage is likewise not accepted from fields alone: the operator clicks "Validate Object Storage Source," the service validates metadata, and submit remains disabled until validation succeeds.

The primary user-facing source state is visible in dynamic panels, not hidden
reference blocks. "System Flow / AWR Intelligence Pipeline" shows current
source mode, active source, source validation, and the Screen 3 handoff target.
"Source Configuration Reference / Staging Context" shows current source type,
current source location, candidate/source metadata, validation state, and
governed handoff status. Both panels update from `selectedSourceMode`, including
Object Storage and Existing Run selections. Raw browser/hash/localStorage state
is moved into a collapsed "Advanced Debug State / Browser Selection State"
block.

## Common Action Payload

Every governed dashboard action includes:

- `request_id`
- `screen_id`
- `action_type`
- `workflow_type`
- `actor_id`
- `requested_at`
- `target_type`
- `target_id`
- `idempotency_key`
- `payload`
- `governance_mode`
- `execution_mode`
- `runtime_influence_granted=false`
- `phase4i_mutation_allowed=false`
- `phase8_behavior=false`
- `direct_truth_mutation_allowed=false`
- `run_analysis_coupling=false`

Requests with Phase 4I mutation, Phase 8 behavior, direct truth mutation, runtime influence, or `run_analysis.py` coupling are rejected by the contract.

## Runtime Workflow Scope

7CM certifies only the index/source-selection workflow. The primary workflow is: choose source mode, configure source metadata, review current source selection, submit governed source-selection handoff, receive request/audit result, and open Screen 3.

Screens 1–6 are not certified by 7CM. Their reusable action definitions and validation hooks may remain in the shared contract for later work, but their current operational panels are not rendered as active generated UI by default in this subphase. The remaining reserved subphases are:

- 7CN Screen 1 Parser Governance Runtime Workflow
- 7CO Screen 2 Diagnostic Review Runtime Workflow
- 7CP Screen 3 Active Re-Analysis Runtime Workflow
- 7CQ Screen 4 Historical Review Runtime Workflow
- 7CR Screen 5 Recommendation / Action / Outcome Runtime Workflow
- 7CS Screen 6 Governance Runtime Workflow
- 7CT Cross-Screen Runtime Workflow Integration

## Screen 5 Deferred Status

Screen 5 remains a required future remediation target. The shared service contract preserves action names for recommendation decision, action assignment/tracking, status update, outcome capture, and feedback-to-learning intent so they can be reused by 7CR, but 7CM does not certify Screen 5 operational readiness.

## Parser Learning And Future-Run Influence

The 7CM bridge preserves the future Phase 7 parser-learning loop in the shared contract: unknown parser signals can be submitted for review, knowledge artifacts can be routed for governed review, parser mapping approval intent can be recorded, and Screen 6 can submit materialization and runtime eligibility requests in their later subphases. In 7CM, only index source-selection requests are certified.

Approved learning is not applied silently. A parser mapping or knowledge artifact can influence future parsing, scoring, or analysis only after governed materialization and explicitly controlled runtime eligibility. The request metadata records that future-run influence must be auditable, explainable, reversible, and limited to future runs. The bridge rejects immediate runtime activation, parser mutation, scoring mutation, recommendation truth mutation, Phase 4I mutation, and Phase 8 behavior.

## Phase 7U Trend-Aware Scoring Preservation

7CM does not change the Phase 7U trend-aware scoring model. `Score(x, t)` remains advisory/shadow context, deterministic scoring remains authoritative, and dashboard controls do not activate trend-aware scoring as runtime truth.

The runtime interaction validator verifies that the 7U artifacts remain present, including `src/learning/trend_aware_scoring.py`, `tests/test_phase7_trend_aware_scoring.py`, `docs/architecture/phase7_trend_aware_scoring.md`, `docs/architecture/phase7_trend_aware_scoring_model.md`, `scripts/run_phase7_ml_validation.py`, and `scripts/run_phase7_ml_readiness_check.py`. 7CM does not modify scoring/runtime integration code. Any future influence on scoring must continue through governed materialization and runtime eligibility.

## Intentionally Preview-Only Controls

Older Phase 7 preview panels remain in the dashboard as historical/read-only context for their original subphase boundaries. They are not used as final operational evidence and must not appear to be the current workflow controls. For 7CM, final operational evidence comes only from the index source-selection workflow and `scripts/run_phase7_dashboard_runtime_interaction_validation.py`.

## Validation

Run:

```bash
python scripts/run_phase7_dashboard_runtime_interaction_validation.py --json
```

The validator checks generated `index.html` evidence, source-selection action metadata, OS folder/file picker support, `.out`-only local AWR candidate support, source metadata payloads, the client-side bridge, the separate service/contract files, absence of contradictory final-operational text, absence of direct `run_analysis.py` button coupling, absence of Phase 4I mutation, absence of direct truth mutation, default-denied runtime influence, and absence of Phase 8 behavior.

The validator also invokes the local service handler in-process, submits valid index source-selection requests for local folder metadata, local file metadata, existing run metadata, and Object Storage metadata, and requires the service response to prove each handoff request was accepted, validated, and queued with an audit reference. It separately exercises service-side existing-run lookup and Object Storage validation. It also submits invalid requests, including HTML AWR input, folders with no AWR candidates, and incomplete Object Storage metadata, and requires rejection.

After regenerating the dashboard with:

```bash
PYTHONPATH=. python scripts/run_analysis.py
```

run the validator again to confirm generated output contains the governed bridge and rendered action controls.

## Readiness Behavior

The 7CI readiness checker treats the index/source-selection portion of dashboard runtime wiring as satisfied only when the 7CM validator passes. Passing 7CM does not globally clear `DASHBOARD_RUNTIME_INTERACTION_NOT_WIRED` or `DASHBOARD_SELECTION_WORKFLOW_UNCLEAR`; Screens 1–6 and cross-screen integration remain pending for 7CN–7CT. 7CZ final certification and the final tag remain pending.

## Phase Boundary

7CM does not mutate Phase 4I, diagnostic truth, recommendation truth, parser output, scoring, or adaptive runtime state. It does not activate ML/adaptive scoring by default, does not grant runtime influence by default, does not hard-code DB or Object Storage credentials, does not wire dashboard buttons directly to `run_analysis.py`, and does not implement Phase 8.

Phase 7 remains incomplete after 7CM. Phase 8 remains not started.
